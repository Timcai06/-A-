## 二、架构审计

### 2.1 分层与依赖方向（合理之处）

- **`src.models`**：基准与短期递推，尽量少依赖分析脚本，符合「核心域在内层」。  
- **`src.calibration`**：依赖 `dynamic_short_term`，通过 `decode_continuous_parameters` 与 `simulate_dynamic_model` 耦合，方向正确。  
- **`src.scenarios`**：依赖校准产物路径（`settings.py`），长期与短期解耦到「读 CSV」边界，可接受。  
- **`src.common`**：`PROJECT_ROOT`、`ensure_parent(s)`、`metrics`、`plotting` 复用面大，是正确抽象。

### 2.2 `src.analysis` 膨胀（主要架构债）

当前 **20+** 个独立脚本平铺在 `analysis/` 下，职责从统计审计、ML 特征、质量闸门、专家质疑到 OVX/GPR 全堆一层。

**风险：**

- 新人难以判断「论文最小闭环」需要哪几条命令（虽在 `docs/02_工程复现.md` 有列表，但**代码层无 DAG**）。  
- 模块间**隐式契约**是「约定文件名」的 CSV（如 `动态模型校准后路径.csv`），无单一 `ArtifactRegistry` 或 schema 校验；改名即多处 grep。

**改进方向（不必一次做完）：** 按域分子包 `analysis/short_term/`、`analysis/long_term/`、`analysis/audit/`，或增加 `src/pipeline/paper_evidence.py` 用函数表显式声明依赖顺序与产物存在性检查。

### 2.3 路径与产物约定（重复字符串）

`PROJECT_ROOT / "output" / "calibration" / "动态模型校准后路径.csv"` 及同类路径在 **10+** 文件中重复出现；`src.scenarios.settings` 与多个 analysis 脚本各自维护一份常量。

**风险：** 重命名输出或迁移目录时易漏改；不符合 DRY。

**改进方向：** 在 `src/common/paths.py` 或新建 `src/common/artifacts.py` 集中声明 `CALIBRATED_PATH`、`BEST_PARAMETERS_CSV` 等，analysis 只 import。

### 2.4 论文构建链路 vs 文档命令（关键缺口）

`scripts/build/build_final_paper.sh` 以 `clean_data` 起头，依次跑 OPEC、市场风险、**情景预测**、大量 `analysis` 与可视化，最后 LaTeX；但**未调用**：

- `python3 -m src.models.baseline_supply_demand`  
- `python3 -m src.models.dynamic_short_term`  
- `python3 -m src.calibration.calibrate_dynamic_model`

**后果：**

- 新环境「只跑 build 脚本」时，若仓库未提交最新 `output/calibration/*.csv`，可能用**旧参数**生成论文图表，与当前 `src` 逻辑不一致且**无失败提示**。  
- 文档 `docs/02_工程复现.md` 要求用户手动跑模型与校准，与「一键论文」**两套真相**，长期易漂移。

**建议：** 在 `build_final_paper.sh` 开头增加可选开关 `FULL_REBUILD=1` 时串联基准+动态+校准；或至少在缺文件时 `exit 1` 并打印「请先运行校准」。

### 2.5 环境可移植性

- `build_final_paper.sh` 内写死优先使用  
  `/opt/homebrew/Caskroom/miniconda/base/envs/mathmodel-oil/bin/python3`  
  对本机友好，对 CI / 队友 / Linux **不友好**。建议仅用 `PYTHON_BIN` 环境变量，路径写进 `docs` 或 `.env.example`，脚本不写死。

- `scripts/project_env.sh` → `env/project_env.sh` 将 Matplotlib 缓存指向项目内 `.cache/`，**设计优秀**，有利于沙箱与无写权限环境。

## 三、代码质量审计

### 3.1 静态与语法

已执行：`python3 -m compileall -q src` — **通过**（无语法错误）。

**SyntaxWarning（应修）：**

- `src/analysis/lagged_risk_index_audit.py` 约第 321 行：字符串中含 `\(` 类转义，未来 Python 可能更严。  
- `src/analysis/short_term_model_fatal_challenges.py` 约第 296 行：同类问题。

建议改为原始字符串 `r"..."` 或写成 `\\(`。

### 3.2 类型与接口

- 核心模型与校准广泛使用 `dataclass` 与类型注解，**可读性好**。  
- 部分 `analysis` 脚本以「过程式 main + 全局 Path 常量」为主，缺少返回类型与小型纯函数抽取，**维护成本偏高**但不致命。

### 3.3 依赖管理

`requirements.txt` 列出 `pandas`、`numpy` 等但**无版本号**。

**风险：** 半年后复现可能出现 API 行为差异（尤其 `pandas 2.x` / `matplotlib`）。

**建议：** 至少对主环境导出 `pip freeze > requirements.lock.txt`，或在 README 写明推荐版本区间。

**未使用或弱相关依赖：** `sqlalchemy`、`psycopg2-binary` 与当前「SQL 草案非主线」并存，增加安装面与审计面；若短期不用可移入 `requirements-optional.txt` 并在文档标注。

### 3.4 测试与回归

- **无单元测试**：`simulate_dynamic_model` 的边界（零缺口、库存耗尽、`day_index` 跳变）无自动化断言。  
- **建议最小集：**  
  - 对 `baseline_price_linearized` / 关键公式做 2～3 个固定数值快照测试；  
  - 对 `simulate_dynamic_model` 用固定小 CSV（3～5 行）断言列存在性与单调性约束；  
  - 对 `encode_continuous_parameters` / `decode` 做往返一致性测试。

数模交卷不一定强制 pytest，但对**你们自己防回归**价值高。

### 3.5 性能与复杂度（提示）

- 校准阶段随机样本 + 差分进化 + 多轮精修，复杂度高属业务需要；`search.py` 中 `workers=1` 避免嵌套并行，**合理**。  
- 若未来扩大网格，可考虑把「评估一次 simulation」抽成可并行任务并控制随机种子可复现性。
